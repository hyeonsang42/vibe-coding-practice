# 틈새진주 — 요구사항 명세

> 어떻게 만드는가. 무엇을·왜는 [plan.md](./plan.md)에 있다.

## 1. 최우선 규칙 — 복귀 보장

```
왕복 이동시간 + 예상 체류시간 + 15분 안전여유  ≤  남은 시간
```

이 조건을 넘는 코스는 **추천 목록에 넣지 않는다.** 정렬 순위를 낮추는 게 아니라 아예 제외한다.
이 제약이 일반 관광 추천과 이 서비스를 가르는 정체성이므로, 다른 요구사항보다 우선한다.

## 2. 기술 스택

| 항목 | 선택 | 비고 |
|---|---|---|
| 프레임워크 | Next.js (App Router) | |
| 언어 | TypeScript | |
| 스타일 | Tailwind CSS | |
| 데이터 | **저장소 안 정적 파일** | Supabase 사용하지 않음 |
| 배포 | Vercel | |

**Supabase를 쓰지 않는 이유**: 시연용 장소·코스는 고정 데이터이고 사용자가 저장할 내용이 없다. 프로젝트 규칙이 "필요할 때만 쓴다"이므로 추가하지 않는다. 나중에 필요해지면 **이 문서를 먼저 고친 뒤** 도입한다.

## 3. 화면 6개

| # | 화면 | 경로 | 담는 것 |
|---|---|---|---|
| 1 | 시작 | `/` | 서비스명, "다음 행사 전, 진주를 한 번 더 만나보세요", 시작 버튼 |
| 2 | 상황 입력 | `/plan` | 현재 위치, 다음 행사·시작시각, 남은 시간, 예산, 관심 분야, 도보 가능시간 |
| 3 | 추천 결과 | `/courses` | 코스 3개 카드 — 소요시간, 복귀 예정시각, 예상 지출, 추천 이유 |
| 4 | 상세 동선 | `/courses/[id]` | 지도 이미지 + 핀·연결선, 이동 순서, 지점별 체류시간, "행사 15분 전 복귀" 표시 |
| 5 | QR 인증 | `/courses/[id]/check-in` | QR 스캔 시뮬레이션 → 방문 인증 완료 + 혜택 표시 |
| 6 | 상권 대시보드 | `/dashboard` | 시간대별 방문자, 상점별 유입, 분산 경로, 예상 소비 연결 |

**지도**: 지도 API를 붙이지 않는다. 지도 이미지를 배경으로 깔고 핀과 연결선만 표시한다.
**QR**: 카메라를 쓰지 않는다. 버튼을 누르면 인증 완료 화면으로 넘어가는 수준이면 충분하다.

### 시나리오 예시 (화면 2~4의 기준값)

현재 위치 축제 행사장 / 다음 행사 19:30 공연 / 현재 18:10 / 남은 시간 80분 / 예산 15,000원 / 관심사 로컬 간식·사진·실내 휴식 / 도보 편도 10분
→ 결과 문구: "왕복 이동 20분, 예상 체류 35분, 복귀 여유 20분입니다. 현재 남은 시간 안에 이용 가능하며, 비가 올 경우 실내 경로로 변경할 수 있습니다."

## 4. 데이터 구조

**Place** (시연용 6~9곳)
`id` / `이름` / `분류` / `위치` / `축제장에서 도보 소요분` / `평균 체류분` / `예상 지출` / `영업시간` / `혜택` / `혼잡도(시연용)` / `실내 여부`

**Course** (시연용 3개 이상, 30·60·90분 구간별)
`id` / `소요 구간(30|60|90)` / `방문 순서(Place 목록)` / `총 소요분` / `예상 지출` / `추천 이유` / `우천 시 대체 경로`

실시간 경로 계산은 하지 않는다. 사전에 만든 코스를 조건에 맞춰 걸러 보여준다.

## 5. AI 처리 구조

생성형 AI가 장소를 통째로 지어내면 근거 없는 결과가 나온다. 3단으로 분리한다.

| 단계 | 하는 일 | 1단계 구현 |
|---|---|---|
| ① 규칙 기반 필터링 | 영업 중 · 남은 시간 내 왕복 가능 · 예산 내 · 접근성 조건 | **앱 안 로직으로 구현** |
| ② 추천 순위 정렬 | 취향 적합도, 복귀 안정성, 이동 효율, 상권 분산, 혜택을 종합 | **앱 안 로직으로 구현** |
| ③ 생성형 설명 | 추천 이유·일정표 자연어 작성, 다국어, 우천·혼잡 시 대체 제안 | **사전 작성 문구로 대체** |

③의 실제 API 호출은 다음 단계로 미룬다 — 발표 중 네트워크나 키 문제로 화면이 비는 위험을 피한다. 발표에서 실호출이 꼭 필요하다면 이 문서를 먼저 고친다.

**다국어(영·중·일)**: 1단계는 한국어만. 보조 기능으로 남겨둔다.

## 6. 접근성과 음성

### 6-1. 접근성 (필수)

시각장애인 사용자는 이미 스크린리더(TalkBack·VoiceOver·NVDA)를 쓴다. 스크린리더가 제대로 읽을 수 있게 만드는 것이 먼저다. (읽어주기 기능은 6-3장에서 따로 다룬다.)

- 화면이 바뀌는 지점(QR 인식 중 → 인증 완료, 추천 결과 없음)은 `aria-live`로 알린다
- **색만으로 상태를 표시하지 않는다.** 인증 완료·공백시간대 같은 표시는 글자나 기호를 함께 둔다
- 슬라이더·입력에는 현재 값을 읽을 수 있는 설명을 붙인다
- 차트는 그림으로만 두지 않고, 같은 내용을 읽을 수 있는 형태로 함께 제공한다
- 키보드만으로 모든 화면을 돌 수 있어야 한다

### 6-2. 음성 입력 (보조)

버튼 대신 말로 상황을 알려주는 방식을 함께 제공한다. 손이 자유롭지 않은 축제장 상황과, 대화형을 선호하는 사용자를 위한 것이다.

- **브라우저 내장 Web Speech API를 쓴다.** 라이브러리·API 키·서버 없이 동작한다
- 받아내는 값은 **시간·예산·관심 분야** 뿐이다. 문장 해석은 규칙 기반으로 처리한다
- 지원하지 않는 브라우저(Firefox 등)에서는 **음성 버튼을 감추고 기존 폼을 그대로 쓴다.** 음성은 유일한 입력 수단이 되어서는 안 된다
- Whisper 등 외부 음성 API는 쓰지 않는다 — 발표 중 네트워크가 끊기면 시연이 멈춘다. ③의 판단과 같은 이유다

### 6-3. 읽어주기 (보조)

추천 코스와 이동 동선을 소리로 들려준다. 대상은 스크린리더 사용자가 아니라 **저시력·고령층·난독증 사용자, 그리고 축제장에서 손이 자유롭지 않은 사람**이다.

- **브라우저 내장 `speechSynthesis`를 쓴다.** 라이브러리·API 키·서버가 필요 없다
- **절대 자동 재생하지 않는다.** 사용자가 버튼을 누를 때만 읽는다 — 스크린리더와 소리가 겹치는 것을 이 규칙 하나로 막는다
- 화면에 보이는 글자를 그대로 읽지 않는다. **소리로 들었을 때 자연스러운 문장을 따로 만든다** (`19:04` → "저녁 7시 4분")
- 재생 중에는 언제든 멈출 수 있어야 하고, 화면을 떠나면 소리도 멈춘다
- 지원하지 않는 브라우저에서는 **버튼을 감추는 대신 왜 안 되는지 짧게 알린다.** 아무것도 안 보이면 사용자도 우리도 원인을 알 수 없다. 읽어주기가 없어도 모든 기능은 그대로 쓸 수 있다

## 7. 표기 의무

혼잡도, 이용 수, 방문자 수, 상점별 유입 등 **모든 가상 수치에 "시연용 데이터" 배지를 화면에 노출한다.**
실제 도입 시에는 QR 이용 로그와 상점 운영자 입력값을 쓰는 구조라고 설명한다. 경제효과 수치는 근거 없이 제시하지 않는다.

## 8. 범위 밖

결제·정산 / 지도 API / 실시간 교통·영업정보 / 로그인·회원가입 / 영수증 OCR / 외부 음성 API(Whisper 등) / **소리 자동 재생**

## 9. 작업 순서

1. Next.js 프로젝트 초기화 + Tailwind 설정 → `npm run dev`로 빈 화면 확인
2. 시연용 Place·Course 데이터 작성
3. 화면 1·2 (시작, 상황 입력)
4. 복귀 보장 필터링·정렬 로직
5. 화면 3·4 (추천 결과, 상세 동선)
6. 화면 5 (QR 인증)
7. 화면 6 (대시보드)
8. 접근성 정비 (6-1)
9. 음성 입력 (6-2)
10. 읽어주기 (6-3)

한 단계가 끝날 때마다 화면에서 확인하고, 언제든 `npm run build`가 통과하는 상태를 유지한다.
